The task is to develop classes that analyze logs of visitors.

Assume a military base. The base is divided into zones. Each zone has its name - a string. There are gates that connect some internal zones, these gates allow in and out, subject to security scan. The gates are bi-directional, the security check takes some time. To save expensive military-grade software, the internal gates do not create any logs.

The military base is connected with the outside world via perimeter gates. The perimeter gates are again bidirectional and connect the outside world with some zones of the base. The perimeter gates do produce logs of people passing through, these logs list date, time, and person name.

Your class is given the description of the base. The description is saved in a file, your method is given file name. Subsequently, there is one or more requests to process the logs. For each such log, the classes calculate the list of people that might have visited given zone in the base. The computation is restricted to a given zone name and (optionally) to a given time interval.

The file with the base description is a text file, the data are structured in lines. Each line contains a three-tuple:

zoneA zoneB securityLevel
where zoneA and zoneB are two strings (no whitespace) that identify a pair of zones connected by the gate. Integer securityLevel is from range 1 to 9 and describes how strict the check is. The bigger the number, the more strict the check is. Subsequently, higher security levels result is longer delays when passing through the gate. For the sake of simplicity, securityLevel=1 means 1 minute delay, securityLevel=2 means 2 minutes delay, ..., securityLevel=9 means 9 minutes delay. A basic solution needs to accept securityLevel=1, higher values are needed in the bonus tests.
The log files provide the information on people that enter/leave the base via the perimeter gates. The logs are produced as a concatenation of logs provided by the perimeter gates:

gate1entries
gate2entries
gate3entries
...
gateXentries
The log generated by a gate starts with a header. The header defines log format, zone name (the gate connects the outside of the base and the given zone) and the number of log entries. There are three supported log formats:
text: TEXT zone N\n:
TEXT is a string that identifies the text format,
zone is the zone name (no whitespace allowed),
N is an unsigned integer that denotes the number of following log entries.
binary, little-endian: 49 49 49 49 LL LL zone NN NN NN NN:
49 49 49 49 4 bytes that identify the format,
LL LL 2 bytes that code 16-bit unsigned integer in little-endian byte order, the number denotes the length of the zone name,
zone a sequence of bytes that form the zone name, the length is given by the length above,
NN NN NN NN 4 bytes that code 32-bit unsigned integer in little-endian byte order, the value denotes the number of following log entries.
binary, big-endian: 4D 4D 4D 4D LL LL zone NN NN NN NN:
4D 4D 4D 4D 4 bytes that identify the format,
the remaining values have the same meaning as in the binary little-endian format. However, the multi-byte values are saved in big-endian byte order in this format.
Following the header, there are N entries, each entry logs one person entering/leaving the base. Log entries are given by the header format:
text: YYYY-MM-DD HH:MI person surname and name(s)\n:
YYYY-MM-DD HH:MI the date and time the person entered/left the base,
surname and name(s) a string that identifies the person.
binary, little-endian: DT DT DT DT LL LL surname-and-name(s):
DT DT DT DT 4 bytes that code 32-bit unsigned integer in little-endian byte order. The number determines the date and time the person entered/left the base. The numeric values is interpreted in bitfields, the bit fields are structured as follows:
      bit 31               16   15                0
          YYYY YYYY YYYY MMMM | DDDD DHHH HHII IIII
     
i.e., the minute is given by bits 0-5, hour by bits 6-10, day by bits 11-15, ...,
LL LL 2 bytes that code 16-bit unsigned integer in little-endian byte order. The number determines the length of the string surname-and-name(s),
surname-and-name(s) a sequence of bytes that form the characters of surname-and-name(s), the length is given above.
binary, big-endian: DT DT DT DT LL LL surname-and-name(s): the format is identical to the binary little-endian format. The differences are multi-byte values that are stored in the big-endian byte order.

the first gate log contains 4 entries (bytes 04 00 00 00 at offset 0011-0014),
the first log entry starts at offset 0015:
date and time is given by four bytes 40 52 a3 7e at offset 0015-0019. The format is little-endian, thus the integer value is 0x7ea35240 = 0b0111'1110'1010'0011'0101'0010'0100'0000. Your program needs to implement three classes that are used to analyze the logs and search for people who may have visited a zone in a given time interval. The classes and the required interface:

CMilBase represents a military base:
implicit constructor
initializes an empty instance.
readBase(filename)
reads the structure of the military base from file named filename. If the file does not exist or if the file contents is invalid, the method throws exception std::runtime_error.
processLog(filename)
the method reads log given by filename, pre-processes it and returns an instance of CVisitorLog for further analysis. Method processLog may be called repeatedly with different log files, each call returns an independent instance of CVisitorLog. We assume the base is initially empty for each cal to processLog. Thus the returned instance of CVisitorLog only contains entries read from filename and does not contain the entries from the previously processed log files. If the log file does not exist or if the file format is invalid, the method throws exception std::runtime_error.
other
you may freely add methods needed in your implementation.
CVisitorLog represents a pre-processed log of visitors:
search(filter)
reads the parameters from filter and determines the list of people who may have accessed the given zone in the given time interval. The time interval and the zone name are given in filter. The result is a set of strings - the names of people who may have visited the zone. The computation needs to analyze the logs and look for people who had enough time to pass through the internal gates to reach the zone and had enough time to leave the base.
other
you may freely add methods needed in your implementation.
CAuditFilter represents restrictions on the searched people:
constructor(zoneName)
initializes the instance. Parameter zoneName is a string with the name of the zone we analyze,
notBefore(y, m, d, h, mi)
sets the lower bound for the time interval. If this restriction is set, then the search only considers visitors who were able to reach the zone at the given date/time y-m-d h:mi or later. If the method is not called at all, then the lower bound is not set.
notAfter(y, m, d, h, mi)
sets the upper bound for the time interval. If this restriction is set, then the search only considers visitors who were able to reach the zone at the given date/time y-m-d h:mi or before. If the method is not called at all, then the upper bound is not set.
other
you may freely add methods needed in your implementation.
Submit a source file with the implementation of classes CMilBase, CVisitorLog, CAuditFilter, and your other support classes. Use the attached source file as a starting point. The attached archive contains the test cases and input files used in the basic test.

Notes:

The mandatory tests check for correct results. Big-endian logs are not tested, the internal gates set securityLevel=1.
The optional test inputs logs in the big-endian format.
The bonus test checks internal gates with securityLevel above 1.
Use the algorithms presented in lectures. The algorithms are enough even for the bonus test.
When passing through the base, we assume that we are only delayed by checks at the internal gates. It takes 0 minutes to pass through a zone, the same applies to the perimeter gates.
The perimeter logs do not include enter/leave information. We assume the base is initially empty. Thus the first time a person is logged means the person is entering the base. The second log entry for that person means the person leaves the base, third is entering, ...
Your implementation must validate the dates/times read from the log files. If the date/time is not valid, e.g., 2026-02-29 12:00, then method processLog must throw exception std::runtime_error.
Consider standard Gregorian calendar when processing dates. Leap years are divisible by 4, not divisible by 100, or divisible by 400. The years range from approx. 1900 to approx. 2100. Thus there is no neeed for any special rule for year 4000.
